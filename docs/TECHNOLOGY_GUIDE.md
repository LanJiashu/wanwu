## 一、大语言模型（LLM）

### 1.1 什么是大语言模型

大语言模型（Large Language Model，LLM）是一种基于深度学习的人工智能模型，通过在海量文本数据上训练，学会了理解和生成人类语言的能力。你可以把它理解为一个"读过万卷书的超级大脑"——它不是死记硬背，而是学会了语言的规律和知识之间的关联。

**核心能力**：
- **文本理解**：阅读并理解文档、法规、手册的内容
- **文本生成**：撰写报告、回答问题、提供建议
- **逻辑推理**：分析因果关系、判断对错、发现矛盾
- **指令遵循**：按照给定的规则和格式执行任务

**我们使用的模型**：

| 模型 | 参数量 | 特点 | 部署方式 |
|------|--------|------|---------|
| Qwen3.6-27B | 270 亿 | 中文能力强，推理能力优秀，Apache 2.0 开源 | 本地部署（RTX 4090D） |
| GLM-5-Turbo | ~400 亿激活 | 编程能力突出，MIT 开源 | 本地部署（RTX 4090D） |
| GLM-5.1 / Qwen3.6-Max | 数千亿 | 最强推理能力 | API 调用（非敏感场景） |

### 1.2 LLM 的局限性

LLM 虽然强大，但存在几个关键局限：

| 局限性 | 具体表现 | 对我们业务的影响 |
|--------|---------|----------------|
| **知识截止** | 训练数据有截止日期，不知道最新信息 | 无法获知最新发布的法规标准 |
| **幻觉问题** | 可能编造不存在的内容 | 可能虚构不存在的法规条文 |
| **无法访问私有数据** | 不知道企业内部文档内容 | 无法直接回答关于公司制度的问题 |
| **无法执行操作** | 只能生成文本，不能调用系统 | 无法查询 ERP 库存、MES 生产状态 |

**正是这些局限性，催生了后面要介绍的知识库、RAG、Agent、MCP 等技术——它们共同弥补了 LLM 的不足。**

### 1.3 LLM 在我们方案中的定位

```
┌──────────────────────────────────────────────────────────────┐
│                    LLM 在方案中的角色                           │
│                                                                │
│  LLM 不是"全知全能的神"，而是"理解力极强的助手"               │
│                                                                │
│  ✅ LLM 负责的事：                                             │
│  · 理解用户意图（"帮我查一下 GB/T 150" → 意图：法规查询）     │
│  · 阅读和分析文本（阅读手册段落，判断是否有错误）              │
│  · 生成自然语言回答（将纠错结果整理为可读报告）                │
│  · 逻辑推理（对比新旧标准差异，分析影响范围）                  │
│                                                                │
│  ❌ LLM 不负责的事（由其他技术补充）：                          │
│  · 提供最新知识 → 由知识库 + RAG 补充                          │
│  · 执行操作 → 由 Agent + MCP + Skill 补充                      │
│  · 多步骤流程 → 由工作流编排                                    │
│  · 持续学习 → 由 Hermes 闭环 + 知识库更新补充                   │
└──────────────────────────────────────────────────────────────┘
```

## 二、知识库（Knowledge Base）

### 2.1 什么是知识库

知识库是企业私有文档的"数字化仓库"。它将 PDF、Word、Excel、PPT 等格式的文档，经过解析、分段、向量化后存储，使 AI 能够快速检索到相关内容。

**类比理解**：知识库就像企业的"智能档案室"——传统档案室需要人工翻找，而知识库可以让 AI 在秒级时间内从数万页文档中找到你需要的那一段话。

### 2.2 知识库的工作流程

```
┌──────────────────────────────────────────────────────────────┐
│                    知识库建设全流程                              │
│                                                                │
│  第一步：文档上传                                               │
│  ├── 支持 PDF/Word/Excel/PPT/TXT/CSV 等 12 种格式             │
│  ├── 支持网页 URL 抓取                                         │
│  └── 文档存储到 MinIO 对象存储                                 │
│           │                                                    │
│           ▼                                                    │
│  第二步：文档解析                                               │
│  ├── OCR 解析：提取文字内容（默认方式）                         │
│  ├── MinerU 模型解析：精确处理标题/表格/公式（高级方式）        │
│  └── 输出：纯文本内容                                          │
│           │                                                    │
│           ▼                                                    │
│  第三步：文档分段                                               │
│  ├── 通用分段：按固定长度切分，检索和召回内容相同               │
│  ├── 父子分段：子段用于检索（短小精准），父段用于召回（上下文完整）│
│  ├── 分段标识：按 \n\n 或自定义分隔符切分                      │
│  └── 重叠设置：相邻分段保留重叠，避免语义断裂                   │
│           │                                                    │
│           ▼                                                    │
│  第四步：向量化                                                 │
│  ├── 使用 Embedding 模型（如 bge-m3）将每段文本转为向量         │
│  ├── 向量 = 文本语义的数学表示（一串数字）                      │
│  └── 存储到 Elasticsearch 向量索引                              │
│           │                                                    │
│           ▼                                                    │
│  第五步：知识库就绪                                             │
│  ├── 可进行命中测试验证检索效果                                 │
│  ├── 可关联到智能体/工作流/问答应用                             │
│  └── 支持关键词标签、元数据、分段编辑等精细管理                 │
└──────────────────────────────────────────────────────────────┘
```

### 2.3 通用分段 vs 父子分段

这是知识库配置中最关键的选择：

```
通用分段模式：

  原文：┌───────────────────────┐
       │ 第3条 锅炉设计压力应   │
       │ 不小于最高允许工作压力 │
       │ 的1.1倍...            │
       └───────────────────────┘
                    │
                    ▼ 分段（每段 500 字符）
       ┌──────────┐ ┌──────────┐ ┌──────────┐
       │  段落 A   │ │  段落 B   │ │  段落 C   │
       │ (500字)  │ │ (500字)  │ │ (500字)  │
       └──────────┘ └──────────┘ └──────────┘
       检索用 ↓       召回用 ↓       ↓
       段落 A         段落 B         段落 C
       （同一段既用于检索又用于回答）


父子分段模式（推荐）：

  原文：┌───────────────────────┐
       │ 第3条 锅炉设计压力应   │
       │ 不小于最高允许工作压力 │
       │ 的1.1倍...            │
       └───────────────────────┘
                    │
                    ▼ 分段
       ┌──────────────────────┐
       │  父段（1000字）       │ ← 召回时返回（上下文完整）
       │  ┌──────┐ ┌──────┐   │
       │  │子段1  │ │子段2  │   │ ← 检索时匹配（短小精准）
       │  │(300字)│ │(300字)│   │
       │  └──────┘ └──────┘   │
       └──────────────────────┘
```

**为什么推荐父子分段**：法规标准文档中，一个条款往往跨越多段。通用分段可能把一个完整条款切断，导致检索时只匹配到部分内容。父子分段用子段精准匹配，用父段提供完整上下文，效果更好。

## 三、RAG（检索增强生成）

### 3.1 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是一种让 LLM "先查资料再回答" 的技术。它将知识库检索与大语言模型生成相结合，解决了 LLM 知识截止和幻觉问题。

**类比理解**：
- **纯 LLM**：像"闭卷考试"——只能凭记忆回答，可能记错或编造
- **LLM + RAG**：像"开卷考试"——先翻书找到相关内容，再基于原文回答

### 3.2 RAG 的工作原理

```
┌──────────────────────────────────────────────────────────────┐
│                    RAG 工作流程                                 │
│                                                                │

│  │  将用户问题通过 Embedding 模型转为向量 │                      │
│  │  "锅炉安全阀排放能力要求" → [0.12, -0.34, 0.56, ...]       │                      │
│  └─────────────────┬───────────────────┘                      │
│                    │                                            │
│                    ▼                                            │
│  ┌─────────────────────────────────────┐                      │
│  │  Step 2：知识库检索                   │                      │
│  │  在向量索引中查找与问题最相似的文档段落 │                      │
│  │                                       │                      │
│  │  三种检索模式：                        │                      │
│  │  ├── 向量检索：按语义相似度匹配        │                      │
│  │  │   "安全阀排放" ≈ "安全阀泄放"      │                      │

│  │  └── 混合检索（推荐）：向量 + 全文融合  │                      │

│  │  使用 Rerank 模型重新评估相关性        │                      │
│  └─────────────────┬───────────────────┘                      │
│                    │                                            │
│                    ▼                                            │
│  ┌─────────────────────────────────────┐                      │
│  │  Step 4：组装 Prompt                  │                      │
│  │                                       │                      │

### 3.3 三种检索模式对比

| 检索模式 | 原理 | 优势 | 劣势 | 适用场景 |
|---------|------|------|------|---------|
| **向量检索** | 将文本转为数学向量，计算语义相似度 | 理解同义词/近义词，"安全阀"≈"泄压阀" | 可能遗漏精确编号 | 语义理解类问题 |
| **全文检索** | 基于 BM25 算法，关键词匹配 | 精确匹配编号和专有名词，"TSG 11"精确命中 | 无法理解同义词 | 精确查找类问题 |
| **混合检索** ✅ | 向量 + 全文融合，取长补短 | 兼顾语义理解和精确匹配 | 计算量稍大 | **推荐默认使用** |

### 3.4 RAG vs 微调：为什么选择 RAG

这是本方案最核心的架构决策，详细对比见下表：

| 对比维度 | 微调大模型 | RAG + 知识库 ✅ |
|---------|-----------|----------------|
| 知识更新 | 需重新训练（数天~数周） | 更新文档即可（分钟级生效） |
| 多部门权限隔离 | 知识混入参数，无法隔离 | 每个部门独立知识库，权限精确控制 |
| 灾难性遗忘 | 新知识可能覆盖旧知识 | 知识外置，不存在遗忘问题 |
| 训练成本 | 每次微调需 GPU 数小时~数天 | 无需训练，仅文档向量化 |
| 可解释性 | 答案内生于参数，无法追溯来源 | 可引用具体文档段落，审计友好 |
| 数据安全 | 敏感数据混入模型参数，删除困难 | 敏感数据留在知识库，可精确删除 |

**核心结论**：对于多部门、需权限隔离、知识频繁更新的国企场景，RAG 是唯一正确选择。

### 3.5 GraphRAG：RAG 的进阶形态

传统 RAG 擅长回答"单文档单段落"的问题，但在"跨文档关联推理"场景下存在局限。GraphRAG（图检索增强生成）通过构建知识图谱来解决这一问题。

```
传统 RAG 的局限：

  问题："湖南博物馆收藏了哪些战国时期的文物？"
  
  文档A提到：湖南博物馆收藏了人物御龙帛画
  文档B提到：湖南博物馆收藏了马王堆汉墓出土文物
  文档C提到：战国时期的文物包括曾侯乙编钟
  
  传统 RAG 只能检索到"文档A"或"文档C"中的一个
  无法将"湖南博物馆"和"战国时期"两个条件跨文档关联


GraphRAG 的解决方案：

  Step 1：构建知识图谱
  ┌──────────┐    收藏于    ┌──────────┐
  │ 人物御龙  │ ──────────→ │ 湖南博物馆 │
  │ 帛画     │              └──────────┘
  └────┬─────┘
       │ 年代
       ▼
  ┌──────────┐
  │ 战国时期  │
  └──────────┘

  Step 2：生成社区报告
  按"湖南博物馆"实体聚类，生成社区报告：
  "湖南博物馆收藏的文物包括：人物御龙帛画（战国时期）、
   马王堆汉墓出土文物（西汉时期）..."

  Step 3：检索时同时召回
  · 实体属性关系（人物御龙帛画 → 收藏于 → 湖南博物馆）
  · 社区报告（湖南博物馆相关文物的完整归纳）
```

**GraphRAG 在锅炉制造企业的应用场景**：

| 场景 | 传统 RAG | GraphRAG |
|------|---------|----------|
| "GB/T 150 涉及哪些相关标准？" | 只能找到 GB/T 150 本身 | 通过"引用关系"图谱找到所有被引用/引用的标准 |
| "安全阀相关的所有法规有哪些？" | 可能遗漏跨文档的关联 | 通过"安全阀"实体聚类，汇总所有相关法规 |
| "新标准发布后影响了哪些文件？" | 无法回答 | 通过图谱关系追溯影响范围 |

### 3.6 RAG 持续学习四层机制

RAG 的"持续学习"不靠修改模型参数，而是靠知识库的持续更新 + 检索策略的持续优化：

```
┌──────────────────────────────────────────────────────────────┐
│                  RAG 持续学习四层机制                           │

## 四、Agent（智能体）

### 4.1 什么是 Agent

Agent（智能体）是具备自主决策能力的 AI 程序。与简单的"问答机器人"不同，Agent 能够理解用户意图、选择合适的工具、规划执行步骤、处理异常情况，最终完成任务。

**类比理解**：
- **普通问答**：像"咨询台"——你问一句，它答一句，不会主动做事
- **Agent**：像"私人助理"——你说"帮我查一下这个标准是否过期"，它会自己决定：先查知识库 → 再联网验证 → 最后给你结论

## 五、Skill（技能）

### 5.1 什么是 Skill

Skill（技能）是 Agent 可以调用的**原子能力单元**，类似于人类的"肌肉记忆"——经过训练后可以自动执行、无需思考的标准化操作。

**类比理解**：
- **Agent** 是"员工"，负责理解任务、做出决策
- **Skill** 是"员工掌握的技能"，比如"会查法规""会纠错""会检查格式"
- **工作流** 是"工作流程"，把多个技能按顺序编排成 SOP

### 5.2 Skill 的特点

```
┌──────────────────────────────────────────────────────────────┐
│                    Skill 的核心特点                             │
│                                                                │
│  1. 原子性：每个 Skill 只做一件事                               │
│     · "法规标准查询" Skill → 只负责查询法规                     │
│     · "文本纠错" Skill → 只负责纠错                            │
│     · 不做超出职责范围的事                                      │
│                                                                │
│  2. 可复用：同一个 Skill 可被多个 Agent/工作流调用               │
│     · "法规标准查询" Skill → 纠错助手用它，审查助手也用它        │
│     · 避免重复开发，一次创建处处使用                             │
│                                                                │
│  3. 可组合：多个 Skill 可通过工作流编排组合                     │
│     · 格式审查 + 文本纠错 + 法规查询 + 标准对比 = 年度审查工作流  │

### 5.5 Skill 在万悟平台中的实现方式

在万悟平台中，Skill 通过以下方式实现：

1. **MCP 工具封装**：将外部系统功能（如焊接质检 API、参数推荐 API）封装为 MCP 工具，Agent 通过 MCP 协议调用
2. **自定义工具**：在万悟平台「资源库 → 工具」中创建 REST API 工具，定义输入/输出 Schema
3. **工作流封装**：将复杂的多步骤操作封装为工作流，Agent 调用工作流即等于调用一个复合 Skill
4. **提示词模板**：将特定领域的专业提示词保存为模板，Agent 使用时自动加载

## 六、工作流（Workflow）

### 6.1 什么是工作流

工作流是将多个 Skill、Agent、大模型节点按业务流程编排的自动化管道，类似于企业的"标准作业程序（SOP）"。

**类比理解**：
- **Skill** 是"单个操作步骤"（如"查法规"）
- **工作流** 是"完整的工作流程"（如"年度审查 = 格式检查 → 纠错 → 法规验证 → 标准对比 → 生成报告"）
- **Agent** 是"执行流程的人"（决定什么时候用哪个流程）

### 6.2 工作流的核心优势

| 优势 | 说明 | 对比 Agent 自由执行 |
|------|------|------------------|
| **流程可控** | 每一步都明确定义，不会遗漏 | Agent 可能跳过某些步骤 |
| **结果稳定** | 相同输入产生相同输出 | Agent 的自由决策可能导致结果不一致 |
| **可调试** | 逐步检查每个节点的输出 | Agent 的决策过程是黑盒 |
| **可审计** | 完整记录每一步的输入输出 | Agent 的中间过程难以追溯 |
| **可复用** | 一次编排，反复使用 | 每次都需要 Agent 重新规划 |

│  · 文本纠错：大模型节点，检查语法/逻辑/数据错误                   │
│  · 知识库检索：RAG 检索法规标准库，获取最新法规原文               │
│  · 法规验证：大模型节点，验证手册引用的标准是否正确且现行有效     │
│  · 标准对比：对比新旧标准差异                                     │
│  · 结果汇总：代码节点，汇总所有检查结果                           │
│  · 报告生成：大模型节点，按格式生成审查报告                       │
│                                                                   │
│  预计耗时：人工审查需 3-5 天 → 工作流自动执行约 30 分钟            │

```

## 七、MCP（模型上下文协议）

### 7.1 什么是 MCP

MCP（Model Context Protocol，模型上下文协议）是一种标准化的工具集成协议，让 AI 模型能够无缝连接各种外部工具和数据源，无需为每个系统单独开发适配器。

**类比理解**：
- **没有 MCP**：每接入一个系统（ERP、MES、WPS...），就要为 AI 单独写一套对接代码，像给每个电器配一个专用插头
- **有了 MCP**：所有系统通过统一协议接入，像用万能插座一样，插上就能用

### 7.2 MCP 的工作原理

```
┌──────────────────────────────────────────────────────────────┐
│                    MCP 工作原理                                 │
│                                                                │
│  ┌──────────────┐         ┌──────────────┐                    │
│  │   万悟平台    │         │  外部系统     │                    │
│  │   Agent      │         │              │                    │
│  │              │  MCP    │  ERP 系统     │                    │
│  │  "查一下采购  │ ──────→ │  MES 系统     │                    │
│  │   订单状态"  │  协议    │  WPS 工作流   │                    │
│  │              │         │  焊接质检服务  │                    │
│  │              │ ←────── │  参数推荐服务  │                    │
│  │  返回结果    │  JSON   │  数据库       │                    │
│  └──────────────┘         └──────────────┘                    │
│                                                                │
│  MCP 协议定义了三个核心概念：                                    │
│                                                                │
│  1. MCP Server：一个提供工具的服务端                             │
│     例：ERP MCP Server 提供 query_order 等工具                 │
│                                                                │
│  2. MCP Tool：MCP Server 提供的具体工具                         │
│     例：query_order、get_inventory、submit_expense             │
│                                                                │
│  3. MCP 调用：Agent 通过标准协议调用 MCP Tool                   │
│     输入：工具名 + 参数（JSON 格式）                             │
│     输出：工具执行结果（JSON 格式）                              │
└──────────────────────────────────────────────────────────────┘
```

### 7.3 MCP 在万悟平台中的使用方式

万悟平台提供两种 MCP 使用方式：

**方式一：导入外部 MCP Server**

```
1. 在「资源库 → MCP 服务」点击"导入"
2. 填写 MCP Server URL（如 http://erp-server:8080/mcp）
3. 点击"获取 MCP 工具"→ 自动发现所有可用工具
4. 确认发布 → Agent 和工作流即可使用这些工具
```

**方式二：创建自定义 MCP Server**

```
1. 在「资源库 → MCP 服务」点击"创建 MCP"
2. 配置 MCP Server 名称和描述
3. 绑定自定义工具（REST API）
4. 获取 API 密钥
5. 对外提供标准 MCP 服务
```

### 7.4 我们企业的 MCP 集成规划

| MCP Server | 提供的工具 | 对接系统 | 实施阶段 |
|-----------|----------|---------|---------|
| **ERP MCP** | query_purchase_order / get_inventory / submit_expense | SAP/用友 | 第二阶段 |

## 八、Hermes（持续学习框架）

### 8.1 什么是 Hermes

Hermes 是由 Nous Research 开源的自进化 AI Agent 框架，核心突破是**闭环学习（Closed Learning Loop）**：Agent 从每次任务中自动提取经验、创建可复用技能、跨会话记忆，越用越聪明。

**类比理解**：
- **普通 AI 助手**：像"实习生"——每次都从头开始，不会积累经验
- **Hermes Agent**：像"老员工"——每次完成任务后总结经验，下次遇到类似任务直接复用

### 8.2 Hermes 的四层记忆架构

```
┌─────────────────────────────────────────────────────────────┐
│              Hermes 四层记忆架构                               │
│                                                               │
│  第一层：工作记忆（Working Memory）                             │
│  · 当前对话上下文，会话结束即清除                               │
│  · 类比：你正在思考时脑中暂存的信息                             │
│  · 对应：万悟平台的对话历史                                    │
│                                                               │
│  第二层：情景记忆（Episodic Memory）                           │
│  · 存储具体会话历史，支持全文检索                               │
│  · 类比：你记得"上次处理类似问题时是怎么做的"                   │
│  · 对应：万悟平台的对话记录 + 日志系统                         │
│                                                               │
│  第三层：语义记忆（Semantic Memory）                           │
│  · 存储抽象概念和事实知识                                      │
│  · 类比：你从经验中总结出的"知识点"                             │
│  · 对应：万悟平台的 RAG 知识库 ← 已有！                       │
│                                                               │
│  第四层：程序性记忆（Procedural Memory）← Hermes 核心创新      │
│  · 存储"如何做"的流程 = Skill                                 │
│  · 类比：你学会的"骑自行车"技能，不用思考就能执行               │
│  · 对应：万悟平台的 Skill 系统 ← 需增强！                     │
└─────────────────────────────────────────────────────────────┘
```

### 8.3 Hermes 的闭环学习机制

```
┌──────────────────────────────────────────────────────────────┐
│              Hermes 闭环学习（GEPA 循环）                       │
│                                                                │
│  ┌──────────┐     ┌──────────┐     ┌──────────┐              │
│  │  G 生成   │ ──→ │  E 评估   │ ──→ │  P 提炼   │              │
│  │ Generate │     │ Evaluate │     │ Process  │              │
│  └──────────┘     └──────────┘     └──────────┘              │
│       ↑                                   │                    │
│       │           ┌──────────┐            │                    │
│       └────────── │  A 应用   │ ←─────────┘                    │
│                   │ Apply    │                                 │
│                   └──────────┘                                 │
│                                                                │
│  G（Generate）：Agent 执行任务，生成结果                        │
│  E（Evaluate）：评估任务执行的质量和效果                        │
│  P（Process）：从执行过程中提炼可复用的经验和 Skill              │
│  A（Apply）：将提炼的 Skill 应用到后续任务中                    │
│                                                                │
│  ──────────────────────────────────────────────────────────── │
│                                                                │
│  实际效果：                                                    │
│  第 1 次："帮我查 GB/T 150" → Agent 查询成功                  │
│           → Hermes 提炼 Skill："法规标准查询"                  │
│                                                                │
│  第 2 次："帮我查 TSG 11" → Agent 直接调用"法规标准查询" Skill │
│           → 速度更快、结果更稳定                                │
│                                                                │
│  第 N 次：Agent 已积累数十个 Skill → 处理能力持续增强           │
└──────────────────────────────────────────────────────────────┘
```

### 8.4 如何将 Hermes 能力引入万悟平台

万悟平台已具备 Skill 系统、工作流引擎和 Agent 框架，可以借鉴 Hermes 的闭环学习机制进行增强：

| Hermes 能力 | 万悟平台现状 | 增强方案 | 实施难度 |
|------------|------------|---------|---------|
| **自主 Skill 创建** | ✅ 有 Skill 系统，但需人工编写 | Agent 完成复杂任务后自动提炼 Skill | ⭐⭐ 中 |
| **Skill 自改进** | ❌ Skill 静态不变 | 记录 Skill 使用效果，定期优化 Prompt | ⭐⭐ 中 |
| **持久化记忆** | ⚠️ 对话历史有留存，但无主动召回 | 增加 Memory Nudge 机制，主动沉淀关键知识 | ⭐ 低 |
| **Nudge 主动提示** | ❌ 无 | 任务结束后提示"是否保存为 Skill？" | ⭐ 低 |
| **GEPA 评估循环** | ❌ 无 | 任务完成后自动评估 + 提炼 + 存储 | ⭐⭐⭐ 高 |

**推荐分阶段引入**：

| 阶段 | 引入能力 | 工作量 | 效果 |
|------|---------|--------|------|
| **阶段一（当前）** | Nudge 提示 + 手动 Skill 创建 | 1-2 周 | 用户可手动沉淀高频操作为 Skill |
| **阶段二（3 个月后）** | 自动 Skill 创建 + Skill 自改进 | 2-4 周 | Agent 自动从经验中提炼可复用流程 |
| **阶段三（6 个月后）** | GEPA 评估循环 + 完整闭环 | 4-8 周 | Agent 越用越聪明，自动优化行为 |

## 十、Embedding 与 Rerank

### 10.1 Embedding（向量化）

Embedding 是将文本转换为数学向量的技术。向量是文本语义的数学表示——语义相近的文本，向量也相近。

```
文本 → Embedding 模型 → 向量（一串数字）

"锅炉安全阀排放能力" → [0.12, -0.34, 0.56, 0.78, -0.23, ...]
"安全阀泄放能力要求" → [0.11, -0.33, 0.55, 0.77, -0.22, ...]  ← 语义相近，向量也相近
"财务报表审计流程"   → [0.89, 0.12, -0.45, 0.33, 0.67, ...]   ← 语义不同，向量差异大

向量相似度计算（余弦相似度）：
"锅炉安全阀排放能力" vs "安全阀泄放能力要求" → 0.95（高度相似）✅
"锅炉安全阀排放能力" vs "财务报表审计流程"   → 0.12（几乎无关）❌
```

**我们使用的 Embedding 模型**：bge-m3（BAAI 北京智源人工智能研究院开源），支持中英文，性能优秀。

### 10.2 Rerank（精排）

Rerank 是对检索结果进行二次排序的技术。初次检索（向量/全文）速度快但精度有限，Rerank 用更精细的模型对 Top-K 结果重新评分排序，提升最终返回结果的准确性。

```
初次检索（Top-10）：
  1. TSG 11 第3.2条... → 相关性 0.85
  2. GB/T 16507 第7章... → 相关性 0.72
  3. 公司内部制度... → 相关性 0.68  ← 不太相关
  4. TSG 11 第5.1条... → 相关性 0.65
  5. ...

Rerank 精排后（Top-5）：
  1. TSG 11 第3.2条... → 精排分 0.96  ✅ 最相关
  2. TSG 11 第5.1条... → 精排分 0.89  ✅ 次相关（初次排第4，精排后提升）
  3. GB/T 16507 第7章... → 精排分 0.82
  4. ...（不相关的结果被过滤掉）
```

## 十一、安全护栏

### 11.1 什么是安全护栏

安全护栏是 AI 系统的"安全带"，对 AI 的输入和输出进行过滤和审核，防止敏感信息泄露、有害内容输出和 Prompt 注入攻击。

### 11.2 安全护栏的工作机制

```
┌──────────────────────────────────────────────────────────────┐
│                    安全护栏工作机制                              │
│                                                                │
│  用户输入 → [输入护栏] → Agent/LLM → [输出护栏] → 返回用户     │
│                                                                │
│  输入护栏：                                                    │
│  · 敏感词拦截：检测输入中的敏感指令                             │
│  · Prompt 注入防护：防止恶意用户篡改系统提示词                  │
│  · 数据脱敏：自动识别并脱敏 PII 信息                           │
│                                                                │
│  输出护栏：                                                    │
│  · 敏感词过滤：防止输出包含敏感信息                             │
│  · 内容审核：确保输出内容合规                                   │
│  · 来源标注：标注回答的知识来源，便于审计                       │
└──────────────────────────────────────────────────────────────┘
```

### 11.3 我们企业的安全护栏配置

| 护栏名称 | 类型 | 规则 | 应用范围 |
|---------|------|------|---------|
| 体系纠错安全策略 | 输入+输出 | 防止非纠错指令注入；防止未核实建议输出 | 体系纠错相关 Agent |
| 财务数据保护 | 输出 | 拦截财务数据关键词（金额、薪酬等） | 所有 Agent |
| 人事信息保护 | 输出 | 拦截 PII 信息（姓名、身份证号等） | 所有 Agent |
| 通用安全策略 | 输入+输出 | 防止 Prompt 注入；防止有害内容 | 全局默认 |
