## 一、项目背景与现状分析

### 1.1 企业现状：信息化系统与数据孤岛问题

贵公司作为锅炉制造行业国有企业，已完成基础信息化建设，现有以下核心业务系统：

| 系统 | 用途 | 现状 |
|------|------|------|
| ERP | 采购、库存、财务、成本管理 | 已采购上线，数据在系统内部流转 |
| MES | 生产执行、工序管理、质量追溯 | 已采购上线，与 ERP 未打通 |
| WPS 工作流 | 审批、协同、公文流转 | 已采购上线，独立运行 |
| PLM | 产品生命周期管理、图纸管理 | 已采购上线，与 ERP/MES 未打通 |

**核心问题：数据孤岛**

```
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│   ERP    │  │   MES    │  │   WPS    │  │   PLM    │
│          │  │          │  │  工作流   │  │          │
│ 采购/库存 │  │ 生产/质量 │  │ 审批/协同 │  │ 图纸/文档 │
│ 财务/成本 │  │ 工序/追溯 │  │ 公文流转  │  │ 生命周期  │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
     ❌              ❌              ❌              ❌
  各系统之间数据未打通，形成"信息孤岛"
  · 采购数据无法自动关联生产进度
  · 质量数据无法回溯到设计参数
  · 审批流程无法触发 AI 辅助决策
  · 图纸变更无法自动通知生产部门
```

**数据孤岛带来的具体影响**：

| 问题 | 影响 | 举例 |
|------|------|------|
| 信息重复录入 | 人力浪费、数据不一致 | 供应商信息在 ERP 和 WPS 中各维护一份 |
| 跨系统查询困难 | 决策效率低 | 想查"某批次产品的采购成本+生产质量"需分别登录两个系统 |
| 数据无法驱动决策 | 错失优化机会 | 生产参数数据在 MES 中，但无法自动分析最优参数 |
| 合规审计困难 | 审计成本高 | 法规标准更新后，无法自动检查所有相关文档是否需要修订 |

### 1.2 AI 化目标：智慧办公 + 智慧工厂

本次 AI 化改造的核心目标是**两个维度**的智能化升级：

```
┌──────────────────────────────────────────────────────────────┐

│  ┌────────────────────────────────────────────────────────┐  │
│  │  目标：让知识流动起来，让决策更智能                        │  │
│  │                                                          │  │
│  │  · 知识管理：法规/标准/制度自动检索、纠错、更新提醒       │  │
│  │  · 文档处理：合同审查、报告生成、公文纠错                 │  │
│  │  · 智能问答：员工随时用自然语言查询公司制度/流程          │  │
│  │  · 流程辅助：审批建议、合规检查、数据汇总                 │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                                │
│  维度二：智慧工厂                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  目标：让生产更精准，让质量更可控                          │  │
│  │                                                          │  │
│  │  · 质量检测：AI 焊缝质检，替代人工目检                    │  │
│  │  · 参数优化：自动推荐最优设备参数，降低操作门槛            │  │
│  │  · 预测维护：设备异常预警，减少非计划停机                 │  │

│  └────────────────────────────────────────────────────────┘  │
│                                                                │
│  两个维度的交汇点：数据打通                                     │
│  · 办公侧的法规标准 → 自动驱动生产侧的合规检查                │
│  · 生产侧的质量数据 → 自动生成办公侧的审查报告                │
└──────────────────────────────────────────────────────────────┘
```

## 三、架构决策：为什么选择 LLM + 知识库而非微调大模型

### 3.1 微调 vs RAG：多部门权限隔离场景深度对比

| 对比维度 | 微调专属大模型 | LLM + 知识库（RAG）✅ |
|---------|-------------|-------------------|
| 知识更新 | ❌ 需重新训练（数天~数周） | ✅ 更新文档即可（分钟级生效） |
| 多部门权限隔离 | ❌ 知识混入参数，无法按部门隔离 | ✅ 每个部门独立知识库，权限精确控制 |
| 知识冲突 | ❌ 财务规则 vs 生产规则混入同一模型导致混乱 | ✅ 各部门知识库独立，查询时按权限路由 |
| 灾难性遗忘 | ❌ 新知识训练可能覆盖旧知识 | ✅ 知识外置，不存在遗忘问题 |
| 训练成本 | ❌ 每次微调需 GPU 数小时~数天 | ✅ 无需训练，仅文档向量化 |
| 可解释性 | ❌ 答案内生于参数，无法追溯来源 | ✅ 可引用具体文档段落，审计友好 |
| 数据安全 | ⚠️ 敏感数据混入模型参数，删除困难 | ✅ 敏感数据留在知识库，可精确删除/隔离 |
| 扩展新部门 | ❌ 需收集数据重新训练 | ✅ 新建知识库 + 配置权限，即开即用 |
| 合规审计 | ❌ 无法证明"没有使用某部门数据" | ✅ 知识库隔离，权限日志可审计 |

### 3.2 多需求 + 权限隔离场景为什么不适合训练一个大模型

```
微调大模型的知识混入问题：

  财务部数据 ──┐
  人事部数据 ──┤
  生产部数据 ──┼──→ 微调训练 ──→ 单一模型（知识混在一起，无法分离）
  体系部数据 ──┤                    · 财务规则影响生产回答
  采购部数据 ──┘                    · 人事信息可能泄露到其他部门回答
                                     · 删除某部门数据 = 重新训练整个模型
                                     · 新增部门需求 = 重新训练

RAG + 知识库的知识隔离方案：

  财务部数据 ──→ 财务知识库 ──→ 仅财务部可见 ✅
  人事部数据 ──→ 人事知识库 ──→ 仅人力部可见 ✅
  生产部数据 ──→ 生产知识库 ──→ 仅生产部可见 ✅
  体系部数据 ──→ 体系知识库 ──→ 仅总师办可见 ✅
  采购部数据 ──→ 采购知识库 ──→ 仅采购部可见 ✅
                                    ↕
                        通用 LLM（不包含任何部门数据）
                        · 只负责理解和生成
                        · 知识来自检索，不来自参数
```

**三个致命问题**：

1. **权限无法隔离**：模型参数是"一坨"数据，无法按部门划分权限
2. **更新成本极高**：法规标准每季度更新，每次更新都需要重新微调
3. **删除困难**：《个人信息保护法》要求可删除个人数据，但微调后数据已融入参数

### 3.3 LLM + 知识库（RAG）方案的持续学习能力

RAG 的"持续学习"不靠修改模型参数，而是靠知识库的持续更新 + 检索策略的持续优化：

```
┌──────────────────────────────────────────────────────────────┐
│                  RAG 持续学习四层机制                           │
│                                                                │
│  第一层：知识库实时更新（分钟级）                                 │
│  ├── 新文档自动入库：上传 → 解析 → 向量化 → 入库               │
│  ├── 过期文档自动标记：关联有效期，过期自动失效                  │
│  └── 增量索引：仅对新/变更文档重新向量化                        │
│                                                                │
│  第二层：用户反馈闭环（日级）                                    │
│  ├── 点赞/踩：用户对回答质量反馈                                │
│  ├── 纠错提交：用户修正错误 → 自动生成新知识条目                │
│  └── 知识缺口识别：高频未回答问题 → 提示管理员补充文档          │
│                                                                │
│  第三层：检索策略优化（周级）                                    │
│  ├── 查询重写：优化模糊查询为精确检索词                        │
│  ├── 混合检索：BM25 关键词 + 向量语义检索融合                  │
│  ├── Rerank 精排：对检索结果二次排序                            │
│  └── GraphRAG：跨文档引用场景启用知识图谱增强检索               │
│                                                                │
│  第四层：模型能力升级（季度/年度）                               │
│  ├── LLM 模型升级：随开源模型迭代升级                          │
│  ├── Embedding 模型升级：更好的向量化模型提升检索精度           │
│  └── Prompt 优化：根据使用数据持续优化提示词模板                │
└──────────────────────────────────────────────────────────────┘
```

## 四、关键问题讨论

### 4.1 幻觉问题：为什么 AI 会"东拉西扯"，我们的方案如何解决

#### 为什么豆包等 AI 会"东拉西扯"

```
┌──────────────────────────────────────────────────────────────┐
│              AI 幻觉（Hallucination）的根源                     │
│                                                                │
│  本质原因：大语言模型是"概率预测机器"，不是"知识检索机器"       │
│                                                                │
│  LLM 的工作方式：                                              │
│  输入前文 → 预测下一个最可能的词 → 再预测下一个 → ...          │
│                                                                │
│  幻觉产生的三种情况：                                          │
│                                                                │
│  1. 知识缺失型幻觉                                             │
│     · LLM 不知道答案，但"编造"了一个看起来合理的回答           │
│     · 例：问"NB/T 47034 最新版是哪年？" → LLM 编造"2023年"    │
│     · 原因：训练数据中没有这个信息，但模型学会了"回答的样子"   │
│                                                                │
│  2. 知识混淆型幻觉                                             │
│     · LLM 把不同来源的信息错误组合                             │
│     · 例：把 GB/T 150 的内容张冠李戴到 GB/T 16508 上          │
│     · 原因：模型参数中知识是分布式存储的，容易交叉干扰         │
│                                                                │
│  3. 过度迎合型幻觉                                             │
│     · LLM 倾向于"顺着用户说"，即使用户的前提是错的             │
│     · 例：用户问"GB/T 150-2011 还有数吗？" → LLM 回答"有数"   │
│     · 原因：训练数据中"肯定回答"比"否定回答"更常见             │
└──────────────────────────────────────────────────────────────┘
```

#### 我们的方案如何解决

```
┌──────────────────────────────────────────────────────────────┐
│              我们的防幻觉方案：五层防线                          │
│                                                                │
│  第一层：RAG 检索替代参数记忆 ✅ 最核心                         │
│  ├── 不让 LLM "凭记忆回答"，而是"先查资料再回答"              │
│  ├── 每个回答都必须基于知识库中检索到的原文                     │
│  └── 效果：知识缺失型幻觉大幅减少                              │
│                                                                │
│  第二层：引用来源强制标注 ✅                                    │
│  ├── 要求 LLM 在回答时必须标注引用来源                         │
│  ├── 例："根据 TSG 11 第3.2条（来源：法规标准库-文档A-第12段）"│
│  └── 效果：无法编造来源，编造的内容无法标注来源                │
│                                                                │
│  第三层：安全护栏过滤 ✅                                       │
│  ├── 输出护栏检测"未核实"的断言                               │
│  ├── 对无法在知识库中找到依据的回答自动标注"建议人工复核"      │
│  └── 效果：即使产生幻觉，也会被标记提醒                        │
│                                                                │
│  第四层：知识库时效性管理 ✅                                   │
│  ├── 知识库文档关联有效期，过期自动失效                        │
│  ├── 法规标准更新后，旧版本自动标记为"已废止"                  │
│  └── 效果：避免引用过期信息                                    │
│                                                                │
│  第五层：人机协同机制 ✅                                       │
│  ├── AI 纠错结果不直接修改文档，而是生成"纠错建议"             │
│  ├── 由人工审核确认后才执行修改                                │
│  └── 效果：最终决策权在人，AI 只是辅助                         │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 准确性保障：能否做到 100% 准确？如何设计人机协同机制

**直接回答：不能保证 100% 准确，但可以通过人机协同机制将风险降到最低。**

| 问题类型 | AI 准确率预期 | 人工复核必要性 | 说明 |
|---------|-------------|--------------|------|
| 引用标准编号错误 | 90-95% | 低 | RAG 检索精确匹配，准确率高 |
| 标准已废止/更新 | 85-90% | 中 | 依赖知识库时效性 + 联网检索 |
| 技术参数错误 | 80-90% | 中 | 数值比对需要精确匹配 |
| 法规虚构 | 95-99% | 低 | RAG 检索无法找到 = 不存在 |
| 语法/逻辑错误 | 85-90% | 中 | LLM 擅长但非完美 |
| 跨文档逻辑矛盾 | 70-80% | 高 | 需要深度推理，AI 最容易出错 |

**人机协同机制设计**：

```
┌──────────────────────────────────────────────────────────────┐
│                    人机协同三档机制                              │
│                                                                │
│  🟢 自动档（置信度 ≥ 95%）                                    │
│  · AI 自动处理，仅记录日志                                     │
│  · 适用：标准编号精确匹配、法规存在性验证                      │
│  · 人工抽检比例：5%                                            │
│                                                                │
│  🟡 建议档（置信度 80-95%）                                    │
│  · AI 生成建议，人工审核确认                                   │
│  · 适用：文本纠错、参数对比、标准差异分析                      │
│  · 人工审核比例：100%                                          │
│                                                                │
│  🔴 预警档（置信度 < 80%）                                     │
│  · AI 标记为"需人工重点复核"                                   │
│  · 适用：跨文档逻辑矛盾、复杂推理、知识库未覆盖               │
│  · 人工必须逐条复核                                            │

### 4.3 数据安全与权限体系

#### 数据分级分类

| 数据等级 | 类型 | 示例 | 处理策略 |
|---------|------|------|---------|
| **L1-公开** | 公开信息 | 国家标准、法规文件 | 可使用 API 模型 |
| **L2-内部** | 业务数据 | 内部制度、操作规程、供应商信息 | 脱敏后可使用 API，或本地模型 |
| **L3-敏感** | 财务/人事 | 财务报表、薪酬数据、员工信息 | **仅本地模型**，数据不出内网 |
| **L3+-机密** | 核心技术 | 核心工艺参数、设计图纸、客户清单 | **仅本地模型 + 物理隔离** |

#### 敏感信息处理方案

```
┌──────────────────────────────────────────────────────────────┐
│                    敏感信息处理流程                              │
│                                                                │
│  用户请求 → 数据级别识别 → 路由决策                             │
│                     │                                          │

### 6.2 私有化部署硬件方案（30 并发显存规划）

**30 并发是关键约束**，需要仔细规划 GPU 资源：

```
┌──────────────────────────────────────────────────────────────┐
│              30 并发 GPU 显存规划                               │
│                                                                │
│  单卡 RTX 4090D（24GB）并发能力：                              │
│  · Qwen3.6-27B Q4_K_M：约 2-4 并发                           │
│  · 30 并发需要：约 8-15 张 RTX 4090D ← 成本过高              │
│                                                                │
│  优化方案：                                                    │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  方案 A：vLLM 多卡推理（推荐）                           │  │
│  │  · 4×RTX 4090D (96GB 总显存)                            │  │
│  │  · Qwen3.6-27B Q8_0 量化 (~34GB)                       │  │
│  │  · vLLM PagedAttention + Continuous Batching            │  │
│  │  · 预计并发：15-25 请求                                  │  │
│  │  · 高峰期溢出请求路由到 API                              │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                                │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  方案 B：本地 + API 混合路由（成本最优）                  │  │
│  │  · 2×RTX 4090D 本地推理（处理 8-15 并发）               │  │
│  │  · 溢出请求自动路由到 API（GLM-5.1/Qwen3-Max）          │  │
│  │  · 数据分级：L3+ 走本地，L1-L2 可走 API                 │  │
│  │  · 30 并发中约 60% 本地 + 40% API                       │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                                │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  方案 C：MoE 高速模型（并发优先）                         │  │
│  │  · 4×RTX 4090D 部署 Qwen3.6-35B-A3B MoE               │  │
│  │  · 仅 3B 参数激活，推理速度 20-34 t/s                    │  │
│  │  · 同等算力下并发能力提升 3-5 倍                         │  │
│  │  · 预计并发：25-35 请求                                  │  │
│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

**推荐方案：方案 B（本地 + API 混合路由）**

理由：
1. 成本可控：2×RTX 4090D 服务器约 6-8 万，API 溢出成本月均 500-2000 元
2. 安全合规：L3+ 数据始终走本地模型
3. 弹性扩展：高峰期自动溢出到 API，闲时全部本地处理
4. 30 并发保障：本地 8-15 + API 弹性补充

**30 并发 GPU 显存分配表**：

| 工作负载 | GPU 显存 | 运行模式 | 说明 |
|---------|---------|---------|------|
| Qwen3.6-27B Q4_K_M | ~17GB × 2 卡 | 常驻推理 | 双卡并行，主力文本推理 |
| bge-m3 Embedding | ~2GB | 常驻推理 | RAG 向量化 |
| bce-rerank | ~1GB | 按需推理 | 检索精排 |
| YOLOv8s 推理 | ~3GB | 按需推理 | 焊接质检（与 LLM 共享 GPU） |
| YOLOv8s 训练 | ~6GB | 离线批处理 | 晚间训练，不影响日间推理 |

### 6.3 混合模式：本地 + API 的数据分级路由

| 数据级别 | 路由策略 | 允许的 API 供应商 | 示例 |
|---------|---------|----------------|------|
| L1（公开） | 可选 API 或本地模型 | 阿里云/华为云/智谱 | GB/T 标准、行业法规 |
| L2（内部） | 脱敏后 API 或本地模型 | 阿里云/华为云/智谱 | 内部制度、操作规程 |
| L3（敏感） | **仅本地模型** | ❌ 禁止任何 API | 财务报表、薪酬数据 |
| L3+（机密） | **仅本地模型 + 物理隔离** | ❌ 禁止任何 API | 核心工艺、客户清单 |

## 八、优先落地场景实施方案

### 8.1 场景一：文本纠错（体系手册/标准/质保/管理制度）

#### 业务分析与痛点

| 纠错类型 | 痛点 | 影响 |
|---------|------|------|
| 引用错误 | 引用了错误的标准编号 | 生产按错误标准执行，安全隐患 |
| 标准过期 | 引用了已废止的标准 | 合规风险，审核不通过 |
| 法规虚构 | 瞎编了不存在的法规条文 | 严重合规风险 |
| 数据错误 | 引用了错误的参数值 | 生产参数错误，质量事故 |
| 语法错误 | 语句不通顺、标点错误 | 文档专业性受损 |
| 逻辑错误 | 前后矛盾、逻辑不自洽 | 执行混乱 |

#### 完整搭建步骤

**步骤一：平台部署（1-2 天）**

```bash
# 服务器配置：1×RTX 4090D + 64GB RAM + 1TB SSD
cp .env.bak .env
# 编辑 WANWU_ARCH, WANWU_EXTERNAL_IP, WANWU_BFF_JWT_SIGNING_KEY
docker network create wanwu-net
docker compose --env-file .env --env-file .env.image.amd64 up -d

# 部署本地模型
docker exec ollama ollama pull qwen3.6:27b
docker exec ollama ollama pull bge-m3
```

**步骤二：构建法规标准知识库（2-3 天）**

| 知识库名称 | 文档类型 | 权限 |
|-----------|---------|------|
| 锅炉法规标准库 | 国家法规、行业标准、安全规程 | 总师办 + 安环 + 质检 |
| 体系管理手册库 | 公司体系手册、管理文件 | 总师办 |
| 质保管理库 | 质保手册、质保程序 | 质检 + 总师办 |
| 管理制度库 | 公司管理制度、操作规程 | 按部门授权 |

关键配置：
- 分段模式：**父子分段**（子段 300 字检索，父段 1000 字召回）
- 检索模式：**混合检索**（向量 + 全文）
- Rerank：开启

**步骤三：创建纠错智能体（1-2 天）**

- 模型：Qwen3.6-27B（本地）
- 知识库：关联上述知识库
- 联网检索：开启（验证标准时效性）
- 安全护栏：配置纠错安全策略

系统提示词核心要求：
1. 严格基于知识库中的权威资料判断，不要凭空推测
2. 每个纠错必须标注依据来源（标准编号 + 条款号）
3. 不确定的内容标注"建议人工复核"
4. 知识库中没有相关信息的，明确告知需人工核实

**步骤四：权限配置与发布（0.5 天）**

- 总师办用户 → 可使用纠错 Agent + 法规标准库 + 体系管理库
- 质检用户 → 可使用纠错 Agent + 法规标准库 + 质保管理库
- 其他部门 → 按需授权

**步骤五：测试验证（1 周）**

| 指标 | 目标值 |
|------|--------|
| 引用错误检出率 | ≥ 90% |
| 数据错误检出率 | ≥ 85% |
| 法规虚构检出率 | ≥ 95% |
| 误报率 | ≤ 10% |

#### 预期效果

- 人工审查 3-5 天 → AI 辅助审查约 30 分钟 + 人工复核 2-3 小时
- 效率提升约 **10-20 倍**

### 8.2 场景二：焊接质检（YOLOv8 + MCP 集成）

#### 业务分析与痛点

- 人工目检速度慢（~2min/张），受疲劳和经验影响
- 漏检率 5-15%，一致性差
- 质检数据无法自动统计分析

#### 完整搭建步骤

**步骤一：数据采集（2-4 周）**

- 产线工位部署工业相机
- 采集焊接图片 1000+ 张，覆盖良好/不良/缺陷
- 额外成本：工业相机 0.5-2 万

**步骤二：数据标注（1-2 周）**

- 使用 Label Studio（开源）标注
- 标注类别：气孔、夹渣、未熔合、焊瘤、裂纹等
- 成本：0 元

**步骤三：模型训练（1 周）**

- YOLOv8s 训练 + Optuna 超参优化
- 复用 RTX 4090D，晚间训练不影响日间推理
- 成本：0 元

**步骤四：推理服务部署（1 周）**

- FastAPI + TensorRT 加速
- RTX 4090D 单图推理 < 20ms
- 成本：0 元

**步骤五：万悟平台 MCP 集成（1 周）**

- 创建"焊接质检"MCP Server
- 定义工具：welding_inspect / defect_classify
- Agent 通过 MCP 调用质检服务
- 用户在万悟对话："检查这批焊接照片" → 自然语言质检报告

#### 预期效果

| 指标 | 人工目检 | AI 质检 |
|------|---------|--------|
| 检测速度 | ~2min/张 | < 1s/张 |
| 漏检率 | 5-15% | < 3% |
| 一致性 | 受疲劳/经验影响 | 稳定一致 |
| 统计分析 | 手工汇总 | 自动生成 |
